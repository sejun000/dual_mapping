\section{Background and Motivation}
\label{sec:bg}

\subsection{Address Translation under a DRAM Budget}
NAND flash is read and programmed in pages (4--16\,KB) but erased only in
much larger blocks, and a page cannot be overwritten before its block is
erased. The SSD controller therefore writes every update out of place and runs
a flash translation layer (FTL) that maps each logical page to its current
physical page. Old copies become invalid, and garbage collection (GC)
reclaims a block by copying its remaining valid pages elsewhere and erasing it.
These copies make the number of pages written to NAND flash larger than the
amount of host writes. The ratio is the write amplification (WA), and spare
over-provisioned (OP) capacity keeps it bounded.

A page-level FTL keeps one entry per 4\,KB logical page, so its table is
about 0.1\% of the capacity and grows linearly with it. Conventional commercial
SSDs keep the whole table in on-device DRAM, but high-capacity QLC SSDs can
hold only a fraction of it because of the cost, power, and
board area that so much DRAM would take~\cite{TODO-dram-cost}. The FTL must then
either keep part of the mapping in flash or map data in larger units. The
three approaches below take these two routes, and each one moves the cost to a
different part of the I/O path.

\textbf{On-demand mapping.}
On-demand mapping stores the page-level table in non-volatile NAND flash as
flash translation pages (FTPs) and keeps only recently used entries in an on-device
\emph{map cache}, as introduced by DFTL~\cite{dftl}. A small global translation
directory (GTD) locates each FTP. A read that misses in the map cache must first read the
FTP and only then the data page, so two flash reads are
serialized on the read path. Evicting a dirty entry also writes its FTP
back, which adds write amplification. LeaFTL~\cite{leaftl} compresses the
map cache into learned linear segments, so the same DRAM covers more pages.
The segments, however, are built only from runs of sequentially placed pages,
and a mispredicted location imposes an extra flash read. For randomly written
data, both FTLs miss often, and every miss turns
one read into two dependent flash reads. Read latency therefore depends on the
map-cache hit ratio, not on the device.

\textbf{Block-level hybrid mapping.}
Block-level hybrid FTLs such as BAST (block-associative sector
translation)~\cite{bast}, FAST (fully-associative sector translation)~\cite{fast}, and
Janus-FTL~\cite{janusftl} map most data per NAND block,
which needs only one entry per block, and absorb updates in a small pool of
page-mapped \emph{log blocks}. When the pool runs out, a log block is reclaimed
by \emph{merging}. The valid pages of a logical block are copied from its data
block and the log block into a free block, and the old data block and log block
are erased. A merge imposes a higher overhead than the GC of a page-level FTL.
Page-level GC picks the block with the fewest valid pages, so it copies few
pages per reclaimed block. A merge instead rewrites the whole data block even
when only a few of its pages were updated, and one log block can hold updates
to many logical blocks, all of which must be merged before it is erased.

The merge copies compete with host writes for NAND bandwidth, which raises
write latency and lowers write throughput. Each merge also rewrites a whole NAND
block, and NAND blocks keep growing with 3D NAND
generations~\cite{TODO-block-size}, so the work behind a single merge grows with
them. CoMap~\cite{comap} selects page or block mapping for each
write request with reinforcement learning, but the data that it maps per block
are still reorganized at NAND-block granularity.

\textbf{Uniform coarse-IU mapping.}
High-capacity SSDs in production avoid both problems by mapping all data with a
\emph{uniform coarse indirection unit} (uniform coarse IU) of 16--64\,KB~\cite{TODO-iu}. One entry per coarse IU
shrinks the table by the coarse-IU size over 4\,KB, so the whole table fits in DRAM:
every read takes a single flash access, and there are no block-level merges. The cost
moves to writes smaller than a coarse IU. The FTL must read the rest of the unit,
merge the new data, and program the whole unit again (read-modify-write, RMW).
The extra reads lengthen the write path, and the rewritten pages raise write
amplification by up to the coarse-IU size over the write size. In our evaluation the
1/8 budget allows a 32\,KB coarse IU (4\,B per 32\,KB), which raises WA by
2.7--3.3$\times$ over a page-level FTL on YCSB-A and YCSB-B.

\subsection{Motivation}
Figure~\ref{fig:motiv} compares the three approaches with a page-level FTL
that keeps its whole table in DRAM. All FTLs run in NVMeVirt~\cite{nvmevirt}
with the same NAND timing and the same 1/8 mapping-DRAM budget. Each bar is the
geometric mean over the 10 workloads of Section~\ref{sec:eval} (real traces,
applications, and raw I/O), normalized to the page-level FTL.

\textbf{On-demand mapping slows reads.}
With mapping misses, DFTL needs 1.46 flash reads per host read and LeaFTL 1.22
(Figure~\ref{fig:motiv}a, where LeaFTL's misprediction reads are not counted, so its
value is a lower bound). Their average read latency is 2.4$\times$ and
1.7$\times$ that of the page-level FTL (Figure~\ref{fig:motiv}b), although the
flash itself is the same.

\textbf{Block-level hybrid mapping and uniform coarse IUs slow writes.}
FAST's block-level merges raise WA by 2.1$\times$ (Figure~\ref{fig:motiv}c),
so its average write latency is 2.4$\times$ that of the page-level
FTL (Figure~\ref{fig:motiv}d) and it delivers only 57\% of the page-level
throughput. The uniform coarse IU avoids merges, but every 4\,KB write becomes an RMW of
its 32\,KB unit: WA grows by 2.2$\times$ and write latency by 2.8$\times$.

DUET, shown for reference, uses the same DRAM budget as the other bounded FTLs and
stays within 1.05$\times$ of the page-level FTL in flash reads per read, average
read and write latency, and WA.

\textbf{Goal.}
An FTL that fits a limited DRAM budget should therefore (i) minimize mapping
reads, so that a host read costs a single flash read as with a uniform coarse IU,
(ii) eliminate block-level merges, and (iii) absorb small writes without RMW.
DUET meets all three by keeping the coarse IU and adding a fine-grained level
within the same DRAM budget.
